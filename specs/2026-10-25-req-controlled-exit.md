# 受控出库与车库门全流程托管

日期：2026-10-25。状态：**待用户评审**。类型：**新功能（实验性，可开关）**。
版本目标：0.9.0。
关联：[车库控制 spec](2026-10-15-spec-garage-control.md)、[v0.8.1 离库修复](2026-10-25-spec-garage-exit-close.md)。

## 背景：这台扫地机为什么特殊

一般扫地机没有门，直接在 App 按开始即可。本屋的扫地机停在**洗衣机柜内**，柜门是它唯一的出口：

- 不清扫时柜门必须关着（生活空间）
- 机器人要出来清扫，柜门必须开
- 机器人出去了，柜门就该关
- 途中回基站充电/洗抹布/集尘，柜门必须开
- 扫完回基站，柜门必须关

**柜门不是清扫的附属品，而是机器人进出房间的房门。** 因此门动作必须和机器人移动严格绑定，只能由 HA 统一编排。

**永远不会有 App 发起的清扫任务。** 所有清扫指令都从 HA 进入集成。集成可以完整拥有整个序列。

## 历史：为什么放弃了「状态变化触发」

最早实现：自动化监听机器人状态变化（如 `dock → cleaning`），检测到就 pause、开门、resume。

**实测失败**：状态变化检测有延迟，机器人已经移动一小段距离；此时 pause 会在柜子窄口处截断正在执行的路径规划；resume 后机器人在狭窄空间从零重新规划失败，**原地打转，永远出不来**。

根因叠加：柜子空间小、出口小、定位特征少，任何中途打断都会让重定位失败。

**结论：不能在机器人移动过程中打断它。** 新方案只发一个明确目标点，让机器人一次走完。

## 起因（2026-10-25）

用户实测：从充电座出发清扫时机器人做定位，**定位过程中往右蹭到柜门旁边那扇关着的门**（用户确认「往右蹭」）。
物理调整已排除（充电座不能移动）。

### 实测几何

```
机器人停靠点（实测）   (25696, 28439)
危险区                x 24997–26069, y 27123–28764
出库方向              -y（地图向下），需走 1316 mm 离开危险区
右侧（+x）余量        373 mm   ← 蹭门方向
```

> `DEFAULT_DOCK_X/Y = (25500, 25500)` 是硬编码几何常量（`safe_zone.py:10-11`），
> 仅作 `suggest_safe_zone()` 原点，**不是**实测位置，危险区判定不使用它。

### 为什么可以用坐标判断（已核实）

`roborock_plus.get_vacuum_current_position` 随时返回原始地图坐标：

```
停靠时: x=25696.0, y=28439.0, position_source="docked_stale_position_replaced"
```

`docked_stale_position_replaced` 表示「与充电座参考一致后被采纳」，**不表示坐标是假的**。
`(25696, 28439)` 确实在危险区内，判定正确。因此到达判定可直接用坐标。

**顶替保护**：`garage_runtime.py:151-152` 要求充电座标记本身落在危险区内才信任顶替值。
本屋充电座 `(25500, 25500)` 的 `y=25500 < 27123`，**不在区内** → 顶替值不被信任 → 不会误判「已出区」。

## 完整流程（用户 2026-10-25 确认）

```
1  自动化触发或手动开始清扫（必须在 HA 侧，集成做大量前置）
2  打开柜门
3  机器人直线驶出基站到危险区之外          ← 新增
4  关闭柜门                                ← 新增
5  开始真正的清扫任务                      ← 修正判据
6  机器人清扫
   6.1 途中回基站（集尘/换水/充电）
   6.2 暂停机器人
   6.3 打开柜门
   6.4 resume 机器人
   6.5 机器人在基站内操作，柜门不关
   6.6 机器人重新出库（自主，不经受控出库）
   6.7 继续暂停前的清扫任务
7  清扫任务结束
8  机器人返回基站
   8.1 暂停机器人
   8.2 打开柜门
   8.3 resume 机器人
9  关闭柜门
```

**第 6.1–6.7、8、9 步均已实现**（`_return_through_door()`、`docked_intermission`、
`session.ended → async_request_close()`），本批不改动，只需回归证明不被破坏。

**本批真正新增：第 3、4 步；修正第 5 步的门判据。**

## 核心问题：第 5 步的门判据是错的

现有 `async_execute()` 在发清扫命令前要求门可通行：

```python
# garage_control.py:483-484
if self.passage_allowed is not True:
    raise GarageControlError('feedback_unavailable')
```

这个前提只在「机器人还在门内、需要穿过门」时成立。而新流程第 5 步时**机器人已经在门外**，
门关着是对的。同一函数服务两种前提，必须按「机器人现在在哪」分支。

**修正**：门可通行的要求，仅在机器人尚未出区时适用。

## 用户故事

- 作为家庭成员，扫地机从充电座出发清扫时不应蹭到柜门旁那扇关着的门。
- 作为家庭成员，出库期间柜门保持打开（否则夹住机器人），到安全点后关闭。
- 作为家庭成员，关门失败时宁可这次不清扫，也要收到明确告警——不要留一扇开着的门然后悄悄扫地。
- 作为家庭成员，清扫途中回基站时柜门保持打开，机器人能自由进出。
- 作为维护者，这个功能必须可随时关闭；`goto` 是否真能避免蹭门无法从软件保证，需要实测。

## 明确非目标

- **不保证消除蹭门。** `goto` 只给终点不给路径；若 `goto` 本身也要先定位并打转，本方案无效。这是实验版性质，必须写入 CHANGELOG 与清单。
- 不在机器人地图写禁区/虚拟墙（无官方 API，手拼 protobuf 会污染地图）。
- 不修改危险区几何。
- 不为中途回洗插入受控出库（命令层被 `task_already_active` 拒绝）。
- 不删除 `garage_guard.py` 的遗留守卫（见 S14.6 说明，本批不动）。
- 不自动重试出库。
